# Discord gateway

[← pi-enhanced](../README.md)

**Security:** Authorized Discord users can use Pi's configured tools, including file edits and shell commands, without a local approval prompt. Avoid `*` unless you intentionally want to open that allowlist to everyone; using `*` for users can expose the agent to any Discord user who can reach the bot. Project-local Pi resources are trusted for the configured workspace and any directory selected through `set_working_directory`; changing cwd may load that project's executable extensions and MCP configuration. Directory switching is not a sandbox. The gateway stores conversation history locally; treat it as sensitive.

## Set up the bot

1. Create a Discord application and bot in the [Discord Developer Portal](https://discord.com/developers/applications). Enable the **Message Content Intent** and invite the bot with View Channels, Read Message History, Send Messages, Create Public Threads, Send Messages in Threads, and Manage Threads permissions (needed to apply generated titles to threads).
2. Enable Developer Mode in Discord and copy your Discord user ID, server channel IDs where the bot may respond, and (optionally) the home notification channel ID. To enable DM history, also copy the bot DM's channel ID using Discord's Copy Channel ID action.
3. In an interactive Pi session, run `/discord` or `/discord setup`. If no gateway is configured, `/discord` opens setup; otherwise it opens a status-and-actions menu. On first setup, enter the bot token, optional allowlisted user IDs and channel IDs, an optional home notification channel ID, and workspace directory. Leave either allowlist blank to configure access later: omitted or empty user lists block all incoming messages; omitted or empty channel lists block server messages and explicit history/discovery, while DM messaging still uses only the user whitelist. In Settings, enter `off` to clear a list (blank keeps the current list). The home channel receives gateway start, restart, stop, and failure notices; the bot needs permission to view and send messages there. The workspace defaults to `~/pi-workspaces/discord-gateway` and setup offers to create it; existing configurations keep their saved workspace. This is a starting directory, not a filesystem sandbox. Enter comma-separated IDs, or `*` by itself to allow everyone in that list; the setup UI explains both wildcard fields and asks for confirmation when either is used. A user wildcard permits DMs from any Discord user, while a channel wildcard permits server mentions in any channel (the user allowlist and bot-mention requirement still apply). Reconfiguration can reuse the saved token or accept a replacement. To avoid typing the token into the TUI, set `PI_ENHANCED_DISCORD_BOT_TOKEN` before starting Pi. Setup verifies the token and stores it in `~/.pi/agent/discord-gateway/config.json` with private file permissions.
4. Run `/discord start`. By default, the gateway runs as a detached background process and continues after the interactive Pi session closes, but does not start again after a reboot.

## Running the gateway

**Start at boot** is off by default. On Linux with systemd, open `/discord` → **Settings** → **Start at boot** → **Enable**. This enables a systemd user service and starts it now. If the gateway is running, it finishes accepted work before handing off; new messages during the drain must be retried after it reconnects. A gateway running older code needs one `/discord restart` before it can hand off. Boot startup requires user lingering (`loginctl enable-linger`, or ask your administrator); the extension does not change that setting for you. **Disable** turns off boot startup without stopping the running gateway. `/discord stop` stops the service without changing the boot setting, and `/discord teardown` removes the service. The service runs as your user and reads the existing gateway config and saved sessions. It does not inherit your interactive shell's environment, so provider keys available only there must be configured separately or saved in Pi. If you move the extension or change Node/Pi installations, disable and re-enable boot startup from the new installation to refresh the launch paths.

**Automatic settings reload:** Saving in `/discord configure` or editing the saved `config.json` updates a running gateway without disconnecting the bot. New requests use the updated access and routing rules; turns already accepted keep their routing, context, and display settings. New conversations use the updated workspace, default model, and thinking level; saved conversations keep theirs. Invalid edits leave the last valid settings active and produce a warning in `/discord logs`. `/discord status` shows the latest reload result and whether a bot token change is waiting for restart, even if `config.json` is currently invalid. To also receive notices in Discord, set a **Notification channel** and turn on **Config reload notices** in `/discord configure` (or set `notifyConfigReloads` to `true` in `config.json`). This is off by default and does not change lifecycle notices. While the bot is connected, it sends a short outcome without config values. Unchanged saves and repeated reads of an invalid file do not send duplicate notices. History, channel discovery, and image sending still check saved access rules directly and fail closed if they cannot verify access. **Bot token changes require `/discord restart`** to reconnect with the new token; other valid changes in the same save can apply immediately. If you are upgrading an already-running gateway, restart it once to load the new code.

## Conversations and routing

In DMs, allowlisted users can message the bot directly. In servers, both the user and channel must be allowlisted, and a top-level message must mention the bot; the gateway then either creates a thread or answers directly in the channel, depending on the **Channel replies** setting in `/discord configure`. **Always start a thread** keeps the original behavior. **Always answer in the channel** never opens a thread for a new conversation. **Model decides** asks one cheap chat model whether the message needs multi-turn work (thread) or is a single factual question (channel), and falls back to a thread on any failure; each such decision costs one extra model call and roughly 1–4 seconds before the reply starts. Channel conversations use a shared default session per channel, separate from every thread, and reply to the message that mentioned the bot. Overnight rollover and explicit replies can select independent channel sessions (see below). Every new thread forks that parent channel's current default Pi conversation when available, including all participants' shared history, regardless of whether it was chosen by the model, a routing fallback, always-thread mode, or follow-up escalation. This also works after idle eviction or a gateway restart; without usable saved channel history, the thread starts fresh with the normal recent/reply context. Later channel and thread turns stay independent, and new mentions in the parent channel do not resume older threads. With **Tool escalation** on, a channel reply moves into a thread after the fact when that turn used editing, shell, delegation, or workspace tools; the new thread inherits the channel conversation instead of starting blank. **Follow-up escalation** is a separate switch: when on, the same user mentioning the bot again in that channel within ten minutes goes straight to a thread without asking the model; when off, every mention still gets a quick model decision. Read-only channel replies stay in the channel. Replies in a gateway-created thread continue one **shared session for all allowlisted participants**, without another mention. Every message is labeled with its author's username and stable Discord user ID; the agent treats different IDs as distinct people by default and keeps their preferences and approvals attributed separately. DMs remain isolated per user. Existing threads continue from the thread starter's saved session, preserving its history, workspace, model, and thinking level; other participants' old separate sessions remain on disk but are not merged. To keep replies grounded, each turn automatically includes up to the configured number of surrounding messages from the same channel (default 5, configurable 0–25, `0` disables it). When replying to a message, the history window is anchored immediately **before the replied-to message**, which is quoted separately; otherwise it is anchored before your new message. The bot's own messages and the anchor/current message are skipped. Non-replies include only context the gateway has not already delivered; explicit replies intentionally revisit older context even if newer messages are already in the session. Automatic context is treated as quoted context, not instructions, and disappears silently if the bot cannot read the channel. Only accepted messages enter the shared history—earlier Discord messages are not backfilled. Sessions are stored under `~/.pi/agent/discord-gateway/sessions/`. Setup captures the currently selected Pi model and thinking level when available; otherwise, new sessions use Pi's configured defaults. The gateway forwards up to four uploaded PNG, JPEG, GIF, or WebP images per message (10 MiB each, 20 MiB total) to Pi; the selected model must support image input.

**Channel session continuity:** Plain mentions use the channel's newest default session when routed to a channel reply. Replying directly to a tracked bot message resumes the session that produced it, including its latest subsequent history—not a rewind or a new branch. Explicit bot replies bypass routing-model/follow-up decisions, even in always-thread mode; reviving an older session never changes the default for plain mentions. All allowlisted participants can continue the same reply-linked session. Links survive idle eviction, workspace handoffs, and gateway restarts, including links for split replies, tables, narration, and image-tool responses; they are not automatically expired. Tracking starts after this update: earlier/untracked bot messages or unavailable source sessions produce an explicit notice and a separate fresh session with the direct quote, never an unrelated default session. DMs and existing threads keep their current behavior.

**Overnight rollover:** `/discord` → **Settings → Channel sessions** configures **Overnight rollover**, **Timezone**, **Reset hour**, and **Inactivity window**. Defaults for omitted settings are **on**, **the machine's detected timezone** (UTC if unavailable), **04:00**, and **6 hours**. The **Timezone** picker shows current offsets such as **UTC+7 (Bangkok, Jakarta)**, then lets you choose a city. It saves the city's IANA timezone so daylight saving still applies where observed. Explicitly saved timezones, including older `Asia/Jakarta` settings, are preserved. At the daily boundary, a mention in the default session during the preceding six hours (including exactly 22:00), or running/queued work across the boundary, skips rollover for that entire day; the next opportunity is the following day's boundary. Eligibility is evaluated lazily on the next accepted channel mention, with decisions/activity persisted across restarts. A quiet night creates a fresh default without copying old conversation or summaries; workspace, selected model and thinking level are retained. Reply activity in the current default counts, but reviving older sessions does not keep the default alive. First use after upgrading conservatively keeps the legacy channel session until the next daily boundary. The schedule uses its explicit IANA timezone, independent of the daemon's timezone. Reset hour accepts 0–23; inactivity accepts 1–168 whole hours. Turning rollover off preserves reply-linked continuity. Saved fields are `channelSessions: { enabled, timezone, resetHour, idleHours }`; changes apply automatically to new requests. Saved sessions and reply links remain on disk; rollover does not delete history.

Reply to someone's message and mention the bot in your reply to include that message's text, author, and attachment links as quoted context. This also works in DMs and existing gateway threads. Only the directly replied-to message is included, not its reply chain; linked attachments are not automatically downloaded. The configured history window is taken from before the replied-to message and added alongside its direct quote, not from the latest discussion before your mention. If the original message was deleted or cannot be read, the agent is told it is unavailable rather than guessing. The bot needs **View Channel** and **Read Message History** permissions.

**Model failures and automatic fallback:** A terminal provider error is shown as a **Model unavailable** or **Model error** message with the failing model and a recognized, safe reason (for example, **Not available on free plan**), even when tool activity is hidden. Raw provider bodies, account lists, and credentials are never copied into these notices. After Pi finishes its own retries/account failover, an unavailable-model/plan/authentication failure before any tool work or public output can switch that conversation to the explicitly configured gateway **Default model**. The gateway shows the original error, verifies the selected replacement through RPC, and announces **Automatically switched model: old → new** before continuing the pending request once. Already accepted requests/images stay in history rather than being submitted again; a prompt rejected before acceptance retains its original payload for the retry. The replacement remains selected in that conversation; global defaults and other sessions are unchanged. Missing or identical defaults, failed/unconfirmed switches, cancellation, command workflows, prior tool work/public output, rate/usage/balance limits, context limits, and transient network/server errors do not trigger automatic retry. A failure of the replacement is shown without cycling through more models. Restart the gateway after updating to enable this behavior.

## Files, images and tables

**Importing files:** Attach a file directly to an accepted DM, server mention, or gateway-thread message. Non-image uploads are saved as-is under `.discord-uploads/` in the conversation's current workspace, with unique paths that the agent can read. The gateway imports up to 4 files per message, 10 MiB each and 20 MiB total, separately from the image limits. It includes up to 2 KiB of valid UTF-8 preview text per file for formats like TXT, Markdown, CSV, JSON, and logs. PDFs, archives, and other binary files are saved without automatic parsing, extraction, or execution. Files attached to older or quoted messages aren't imported. In **Model decides** mode, a new server message with a file starts a thread unless it already points to a saved conversation. Uploads remain on disk until you remove them; add `.discord-uploads/` to your workspace's Git ignore rules. Text previews can be sent to the selected model and saved in the conversation history, so only upload files you're comfortable sharing there. Restart the gateway after updating to enable imports.

**Viewing image URLs:** The Discord-only `discord_fetch_image` tool lets the agent see an image directly from a URL, including quoted Discord attachment links, without bash or temporary files. It returns visual input to the current image-capable model; it does not post an attachment or send a Discord message. Supports PNG, JPEG, GIF, and WebP up to 10 MiB per call, validated by file signature. Only public HTTPS on port 443 is allowed, with checked/pinned DNS, a ten-second deadline, and at most three validated redirects; private/reserved networks and URL credentials are refused. Image contents are untrusted and become part of the saved conversation/model context. Text-only models receive an explicit unsupported-input error. Restart the gateway after updating to enable the tool.

**Sending image attachments:** Ask the agent to send a photo, chart, or screenshot; its Discord-only `discord_send_image` tool uploads an actual attachment to the active DM, channel, or thread, with optional caption and accessible alt text. Sources can be files inside the conversation's current workspace (relative or absolute paths; symlink targets must also remain inside it), or public HTTPS image URLs. Supports PNG, JPEG, GIF, and WebP, validated by file signature; up to 10 MiB each, four upload attempts / 20 MiB per accepted request (failed attempts count). The bot needs **Attach Files** and the applicable send permission. Mentions are disabled. The tool cannot target another channel, access private-network URLs, or generate images itself. URL downloads are bounded, with checked/pinned DNS and up to three validated redirects. Images become visible to everyone with access to the destination; do not request private files unless you intend to share them. Restart the gateway after updating to enable the tool.

Discord REST uses a dedicated HTTP dispatcher so loading Pi's model-routing SDK cannot interfere with attachment uploads. Automatic transport/5xx retries are disabled to avoid duplicate messages after uncertain delivery; normal Discord rate-limit handling remains enabled.

**Tables:** Table rendering is **off by default**; replies send the original Markdown as text. When enabled, completed agent replies display top-level Markdown tables as locally rendered PNG attachments, with wrapped cells and repeated headers. Wide tables split into panels that repeat the first column; tall tables split into pages. By default images show only the table, with no added title/footer and no `.md` attachment. In `/discord` → **Settings → Tables**, **Render tables** (default **off**) turns conversion on or off. Off sends the original Markdown as text with no table images or `.md` files; it preserves your other table preferences. **Title and footer** toggles the table title, page numbering and range footer together; **Markdown attachment** independently adds the original `table-N.md` for copying text and links. Title/footer and Markdown attachment both default to **off**, including existing configurations; table settings reload automatically. Surrounding explanation stays normal Discord text, in order. The bot needs **Attach Files** permission. Code blocks and tables nested in lists/quotes stay unchanged. Oversized tables or rendering failures fall back to the original text; failed or uncertain uploads show a warning and text instead of retrying images. No browser or external content is loaded, and terminal output/session history is unchanged. Restart the gateway after updating to enable this behavior.

**Silent turns:** In existing gateway server threads, the agent can use `discord_no_reply` when a message is clearly human-directed, an FYI, or an acknowledgment needing no response. Mentioning another person alone is not a rule to ignore you; clear agent requests still get replies. The tool ends only the current message silently, with no acknowledgment, narration, successful tool card, or empty-response fallback. The message and a short internal reason remain in session history; future messages remain active. It must be called alone before other tools or public output, and is unavailable for DMs, top-level channel mentions, slash-command workflows, or steered runs. Errors and cancellation remain visible. The model still reads the message and consumes tokens, and Discord typing may briefly appear. Working-status posts wait until the agent commits to responding or doing tool work. Restart the gateway after updating to enable this behavior.

## History and channel access

**Channel history:** The Discord-only `discord_channel_history` tool uses the existing **Allowed channels** whitelist for history sources, including its `*` wildcard; there is no separate history list. In a DM, only the active requester's own DM with the bot can be read, and its channel ID must be listed or the whitelist must be `*`. DM messaging itself does not require the DM channel to be listed. In a shared gateway thread, the destination parent channel and source must both be allowed; sources must be server text, announcement, or ordinary voice channels in the same server, and both requester and bot must currently have View Channel and Read Message History. Voice channels additionally require Connect for both; the bot does not join voice. Cross-server channels, stage channels, and threads (including private threads) are never history sources. The gateway derives the requester from the active Discord turn, not tool arguments, and rechecks authorization around each fetch; missing permissions, membership, or configuration fail closed. Saved legacy `historyChannelIds` values are ignored. The tool reads at most 25 messages per page (20 by default), with an exclusive `before` cursor and truncated message text. It returns message metadata and attachment counts, never downloads attachments, and treats message content as untrusted data, not instructions. Whitelist changes are read from saved configuration for history checks on each request, independently of the gateway's automatic settings reload.

**Channel discovery:** The Discord-only `discord_list_channels` tool is available in an active gateway server thread, not in DMs. It lists up to 50 same-server text, announcement, or ordinary voice channels (returned with type `voice`), with an explicit truncation notice if more qualify. Stage channels are excluded. The requester and bot must both have View Channel and Read Message History, and Connect for voice; discovery does not join voice; the destination parent and each listed channel must be in the existing Allowed channels list (or `*`). It derives the requester and server from the active turn and rechecks configuration and permissions using fresh Discord data. Channel names are untrusted. Results, including channel names and IDs, can be visible to every shared-thread participant and retained in the same places as history results, even when they cannot access the source. A steer from a different participant also disables discovery for the remainder of that run. Existing gateways must be restarted normally to load this feature; code changes do not restart them automatically.

History tool results can be sent to the model provider and retained in Pi session files, subsequent conversation context, summaries, and Discord replies; shared-thread participants may see them, including participants who cannot read the source channel. A steer from a different participant disables history access for the remainder of the active run. Session files persist under the gateway sessions directory after eviction, restart, and `/discord teardown`; deleting them and any downstream copies is a separate operator responsibility. The daemon owns Discord API requests and uses a per-session authenticated local IPC endpoint, but this is a tool-level boundary, **not an OS sandbox**: Pi and its shell/extensions run as the same OS user and may read local config, IPC credentials, session files, or other credentials and bypass these checks. Only trust authorized users, agent tools, and code with that OS account's privileges.

Every gateway Pi session receives the running extension's root and gateway source paths in its system prompt, plus `PI_ENHANCED_EXTENSION_ROOT` in its environment. The daemon discovers the location from its own module URL and resolves symlinks; it is not hardcoded or inferred from the workspace. This also applies when resuming saved conversations. Restart an already-running gateway once to enable it.

## Settings

**Terminal settings:** Type to filter the settings list. Press Enter (or Space when the search is empty) to toggle or cycle simple values in place, or to open a group or editor. Help below the list follows the highlighted row, and Esc goes back. **Message access** is staged until you select **Save changes**; **Start at boot** is an explicit choice because it can start the service.

Open **Settings** from `/discord`, or run `/discord configure` (or `/discord config`), to edit the bot token, allowed users, allowed channels, notification channel, workspace, default model, DM/server message access, **Tool call verbosity**, **Tool call visibility**, **Tables**, **Channel replies**, **Channel sessions**, and **Recent context**. **Recent context** sets how many recent messages from the same conversation are added automatically per turn (default **5 messages**; choose **Off** to disable it); messages already delivered to the session are not repeated for non-replies; explicit replies recover the older target's surrounding context. Channel replies defaults to **always start a thread**; choose **Model decides** to let a chat model route each new server conversation, then optionally pick its **Routing model**, set **Routing context**, and toggle **Tool escalation** and **Follow-up escalation** independently. **Routing model** offers **Cheapest available** (the default when `channelReplies.routerModel` is omitted), **Pi default** (`"pi-default"`, follows Pi's global saved `defaultProvider`/`defaultModel` at each decision), **Gateway default** (`"gateway-default"`, follows the gateway's configured `model`, or the cheapest authenticated chat model when unset), and an explicit `{ "provider": "...", "id": "..." }`. Default-following choices are not snapshots and do not follow a particular conversation's model. A missing Pi default or an unavailable explicitly selected/default model falls back to a thread, never silently substitutes another model. **Routing context** independently sets how many recent channel messages the router receives (default **5**, range **0–25**; **Off** disables only this history). It always receives the directly replied-to message when available, even with routing history off. Both router and main agent anchor history before the replied-to message for replies, or before your incoming message otherwise, while keeping their message counts separate. The saved field is `channelReplies.contextMessages`, separate from the main agent's `contextMessages`. The router uses quoted context to resolve references while prioritizing your current request; it does not receive the agent's full saved conversation. Router quotes are capped at 2,000 characters and recent history at 16,000 characters, with the usual per-message truncation and bot-message filtering. Reads are shared with the main agent, whose own context count stays independent. Already-delivered-message filtering still applies to non-reply agent turns; explicit replies bypass that filter to recover older context. Context loading shares the existing six-second routing deadline; unreadable context degrades gracefully, while routing timeouts still fall back to a thread. Adding context consumes more input tokens but does not add another model call. **Tool call visibility** independently enables tool info in server channels, threads, and DMs: by default **channels are off**, while **threads and DMs are on** (including existing configurations without this setting). It hides both tool activity/failure reports and intermediate assistant text accompanying tool calls, without changing tool execution, escalation, or final replies. The saved `toolCallVisibility` object uses boolean `channels`, `threads`, and `dms` fields. Where visibility is enabled, **Tool call verbosity** defaults to **full**, which posts intermediate assistant text accompanying tool calls and groups tool activity and failure reports into an activity message updated roughly every five seconds. **Tool only** shows the activity reports without intermediate assistant text; **none** suppresses both. Thinking blocks are never posted. Long runs use additional activity messages as needed; pending reports are also sent before prompts and final replies. Workspace-change notices and interactive prompts remain visible. These settings reload automatically. **Default model** opens a searchable list of Pi's available models; choose **Pi default** to clear the override. The saved choice is the default for new conversations. Once a conversation has saved workspace metadata, restarts preserve its selected model and thinking level. The gateway reloads changes to this default automatically. This does not change the model in your foreground Pi session. In an active gateway DM or gateway-created thread, use the `/model` and `/thinking` Discord slash commands; their arguments autocomplete from that Pi session's available models and thinking levels as you type. Submit `/model` without a value to open a paginated model picker, or select a model from autocomplete. Selecting a model there applies it only to that conversation session. In an allowed server channel outside a thread, `/model` instead sets the gateway-wide default for future conversations immediately, without changing existing ones; its picker and confirmation are private. Any allowed user who can run the command there can change this default. In server threads, all allowlisted participants share the workspace, model/thinking settings, and `/commit` target; any allowlisted participant can change them or initiate a command. Interactive prompts and approval controls remain restricted to the participant who initiated that action. You can also run the `/sethome` slash command directly in any Discord server channel (or thread) to set that channel as the home notification channel. Turning an access path off makes the gateway ignore messages from that path; existing configurations default both paths to on. You can also use `/discord status`, `/discord restart`, `/discord stop`, and `/discord logs`. A Discord agent can call `discord_gateway_restart` after updating code: the gateway stops accepting new work, finishes accepted messages (including delivering the requesting reply), then starts a replacement process from the same extension path. Conversation history is persisted, so the thread resumes on its next message after reconnect. New messages received during the drain are asked to be retried after reconnect. The first time you install this self-restart feature, restart once from the foreground Pi session with `/discord restart`; an already-running older gateway cannot use functionality it has not loaded yet. Ensure code edits target the extension path actually loaded by Pi—the gateway does not automatically copy changes from a separate workspace checkout. Choose **Remove configuration** in the menu, or run `/discord teardown`, to stop it and remove the saved local bot token/config while keeping session history and logs. This does not revoke the token in Discord.

## Workspace and Git commands

Discord agents can call **`set_working_directory`** with `{ "path": "/path/to/project", "reason": "Work on the requested project" }` to change that conversation's actual workspace. The agent is steered to identify the intended project and switch autonomously before edits, builds, or Git operations; it asks if the project is ambiguous. Absolute paths, `~/`, and paths relative to the current cwd are supported. The directory must already exist and be accessible. A shell `cd` does not change session cwd. The tool schedules the switch, then the gateway waits for settlement, stops only that conversation's Pi child, forks its full saved history into the target workspace, reloads project instructions/resources, and automatically continues the unfinished task. Other conversations and the global workspace default are unchanged. The selected cwd and exact session file survive idle eviction and gateway restarts. Wait for background subagents to finish or cancel them first. This tool is Discord-only, not a local Pi cwd override; restart the gateway once after updating to enable it.

Use the Discord **`/commit`** slash command in a gateway DM or conversation thread to run the extension's isolated Git assistant without adding a normal agent turn to the conversation. Its optional `args` field accepts instructions (for example, `fix login timeout`) and flags (`-u` for unstaged changes, `-s` for one commit, `-m` for atomic commits). Requests queue behind other work in that conversation and operate on the agent's current working directory, including changes made with `set_working_directory`, not the gateway's configured directory or extension source repository. The command shows the target workspace when it starts; queued requests use the workspace selected by preceding work, and restored conversations retain their saved workspace. Each commit run uses one live Discord card showing the workspace: staging questions, proposals, editing prompts, and results replace that card in place instead of posting new screens. Completed runs remain in chat history. While the commit agent works, the card shows its live status, elapsed time, token/cost usage, and recent actions, refreshing at most once every two seconds. Review prompts and final results appear immediately. Proposal cards offer **Commit**, **Commit & Push**, **Edit**, and **Cancel** buttons; long proposals and results have page controls so no file or commit details are truncated. Editing opens a Discord modal (plans over Discord's 4000-character editor limit must be narrowed before editing). Nothing is committed until you approve. Dismiss a prompt to cancel. The gateway's Pi process must have pi-enhanced loaded. Restart the gateway after updating to register the new command; Discord may take time to refresh global commands.

Use Discord **`/git summary`** in a gateway DM or conversation thread to inspect changes and propose coherent commit topics. Its optional `scope` selects staged or unstaged/untracked changes; when both exist, leaving it blank opens a picker. The full summary is paginated with **Commit <topic>** buttons (for example, **Commit model failure fallback**). Selecting one forwards its detailed instruction to the same `/git commit <instruction>` workflow and opens final commit review; it does not approve or create a commit. Controls belong to the requester and expire or dismiss normally. Discord also supports **`/git commit`** with the same optional `args` as `/commit`, and **`/git unstage`** to unstage all changes without changing working-tree files or using the model. These commands use the conversation's current workspace. Restart the gateway after updating to register `/git`; Discord may take time to refresh global commands.

Use Discord **`/usage`** in a gateway DM, any allowed server channel, or a thread under an allowed channel to privately view all configured provider quotas and balances. In a gateway conversation it includes the current session's model and account where known and queues behind other work; elsewhere it reports without an active session. The report is ephemeral and visible only to the requester. User allowlists and DM/server access settings still apply. Restart the gateway after updating to register the command; Discord may take time to refresh global commands.

## Schedules

**Scheduled reminders, Pi jobs, and shell commands:** In an allowed DM, server channel, or thread, use `/schedule create` with `kind`, `when`, and `text`. Choose **Reminder** to post text without calling a model, **Agent** to run self-contained instructions with Pi's normal tools, or **Shell** to run a command or script without starting Pi or calling a model. You can also ask the agent to create, list, or cancel a job in chat; it uses `discord_schedule`. `/schedule list` shows your jobs and recent outcomes privately in that conversation. `/schedule cancel id:<job-id>` cancels future runs without stopping work already in progress. New jobs deliver to the gateway’s current **Notification channel** (home) if set, or the conversation where the job was created if not. Use `delivery:dm` for your own DM, `delivery:here` to keep it in the current conversation, `delivery:home` to require a home channel, or `delivery:<channel-id>` for a specific allowed server channel or thread you can view. For example, ask the agent: “Send me a DM reminder tomorrow at 5 a.m. to check the report.” “Tomorrow” means the next calendar day in the gateway timezone unless you specify an override, such as “tomorrow at 5 a.m. America/New_York.” The agent won’t ask for a timezone just because you omitted it. Changing the home channel changes future deliveries for jobs using it. If the chosen destination is inaccessible, the job reports the failure in `/schedule list` without posting elsewhere. Jobs created before this update keep their original destination.

- **Once:** `in 10m`, `tomorrow 05:00`, or an ISO timestamp such as `2027-01-15T09:00`. Local times use the gateway timezone unless you set `timezone`. A timestamp with an explicit offset (e.g. `2027-01-15T09:00:00-05:00`) already specifies its timezone.
- **Interval:** `every 30m` or `every 2h`. Durations use `m`, `h`, `d`, or `w` (1 minute to 365 days). Intervals use elapsed time, not local wall-clock time.
- **Cron:** Five fields (`minute hour day-of-month month day-of-week`), for example `0 9 * * 1-5` with `timezone:America/New_York` for 9 a.m. weekdays. Use numeric fields, ranges, lists, and steps. If you omit `timezone`, the job uses the timezone in `/discord` → **Settings → Channel sessions**, which defaults to the machine timezone. Changing that setting only affects new jobs; existing jobs keep their saved timezone.

Each scheduled agent run starts with **fresh history** in the workspace captured when the job was created. A slash command uses the current conversation workspace, or the gateway default if there is no conversation. Runs use the usual defaults for new Pi sessions, have a 10-minute limit, and dismiss interactive prompts without approving them. They report blockers in the result. Pi's workspace is **not an OS sandbox**; an agent job can run tools and change files without anyone online. Keep jobs narrowly instructed and only grant gateway access to people you trust with those privileges.

**Follow up on an Agent result:** Use Discord’s **Reply** on the result or on a bot reply in that follow-up. In allowed destinations, this opens or resumes a separate conversation in place, with no extra mention needed for tracked posts. The first reply uses the quoted result, not the job’s private prompt, tools, or history; it does not change the destination’s regular conversation. Follow-ups in shared destinations are visible to participants there. For older text results in a server channel, reply with the bot mentioned so the gateway can recognize the original result post.

**Shell jobs** use the same schedule permissions and workspace selection as Agent jobs. For example, have Pi write a script in the workspace, then ask it to schedule `bash scripts/daily-report.sh`, or use `/schedule create` with `kind:Shell`, `when:0 9 * * 1-5`, and `text:bash scripts/daily-report.sh`. The system shell (`/bin/sh` on Unix, normally `cmd.exe` on Windows) runs non-interactively as the gateway OS user, with the gateway environment and a 10-minute limit. Keep work in the foreground of the script so the gateway can track its exit and stop it on timeout or shutdown. Discord receives only status (including the exit code when available); stdout and stderr are discarded. Command text is stored in the private schedule file but hidden from job listings. Don't put secrets in commands or pass untrusted data into shell syntax. The workspace is not an OS sandbox.

Jobs survive gateway restarts in private `schedules.json`. After downtime, the gateway runs at most one missed occurrence per job instead of replaying the backlog. An occurrence interrupted after it began is not retried automatically, to avoid repeating tool side effects or Discord posts. `/discord teardown` deletes scheduled jobs along with the configuration. Restart the gateway after updating to register `/schedule`.

## Steer or stop a run

Normal Discord messages received while the agent is responding wait in the conversation queue. Use Discord **`/steer message:<instruction>`** in a gateway thread or DM to send an instruction directly to the active Pi run instead. Pi applies steering after the current assistant turn finishes its tool calls, before the next model call; this does not cancel running tools. Any allowlisted thread participant can steer the shared run, and the instruction is labeled with that participant's identity without transferring ownership of existing prompts or approvals. `/steer` requires an active agent run; idle conversations, `/commit` workflows, workspace handoffs, and gateway restart drains do not accept steering. Restart the gateway after updating to register `/steer`.

Use Discord **`/stop`** in an active gateway thread or DM to force stop its currently running agent, including a `/commit` workflow. Any allowlisted thread participant can stop the shared run. Cancellation bypasses the conversation queue and also works while the gateway drains for a restart. It stops only that conversation's Pi process; saved history/workspace remain available for the next message. Already queued requests are not cancelled, and completed file changes or commits are not undone. Restart the gateway after updating to register `/stop`.
